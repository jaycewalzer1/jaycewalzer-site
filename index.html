Kokopelli 2026

An open-weight LLM agent living a generated life inside a world model I built: an Unreal city, painted into real-looking video by Cosmos, seen and acted on by Qwen. Runs on one laptop, with a 5-arm study on whether lived experience changes a model.

code ↗kokopelli-labs.com ↗

read more

Kokopelli is an agent that lives inside a world model. A SimWorld city in Unreal holds the physical truth. Cosmos3-Nano-Sim-Transfer paints that sim into realistic video from its control videos (depth, segmentation, edges, blur). A Qwen3-VL-8B agent sees only that painted video, plus words for what its body feels ("you feel shaky and empty inside", never a number), decides, and its action lands back in the sim. Everything runs locally on Apple silicon.

The question behind it: does living through experience, with a LoRA updating the weights each night while the agent sleeps, shift a model differently than simply telling it the same facts? I'm testing that as a 5-arm study: the adapter trained on its own lives, the untrained model, the same model told every effect in its prompt, and two controls trained with the same code (one rewarded for more of everything, one with shuffled rewards).

The first 25-day lived run finished end to end: 99 decisions, 25 trained nights, MMLU unchanged at 75.0. Its honest result is that the choices mostly matched the untrained model's prior, so the next runs raise the sampling temperature and add flipped and shuffled arms to tell learning from prior.

Python, MLX, Qwen3-VL-8B, Cosmos3-Nano, Unreal Engine (SimWorld), LoRA

Talisman 2026

AI teammates in bughouse chess deciding whether to think, talk or move, all on one clock. I fixed the engine's macOS search bug (24 → 657 nodes in 3 s) and train the scheduler on Georgia Tech's PACE cluster.

code ↗code ↗

read more

Talisman is my research code for one question: how should AI bughouse teammates share time and computation between thinking, talking and moving?

Bughouse is chess for two teams of two on two boards. When you capture a piece it goes to your partner, who can drop it onto their own board as a move. Everyone is on a clock, and a checkmate or a flag on either board ends the game for both. So each turn is a choice: think longer, ask for a piece, or sit and wait for one while the clock runs.

I build on Hivemind, an AlphaZero-style bughouse engine. Before adding anything I fixed its baseline on macOS: a -Ofast finite-math flag was making search selection return nothing (24 nodes in 3 s); after the fix the C++ suite passes 296/296. On top, an arena runs four players on a shared simulated clock with partner messages (need, have, sit, go), and a small scheduler policy, trained with REINFORCE on team wins, decides around the frozen engine: move or wait, what to say, and how long to think. A 3D viewer replays every game.

C++, Python, PyTorch, ONNX Runtime, Fairy-Stockfish, React, three.js, Vite

RSI-RL 2026

A self-improving factory for RL coding tasks: mines real developer complaints, checks them against papers, and holds every task near a 25% frontier pass rate behind a 7-stage test gate.

code ↗

read more

RSI-RL is a self-improving factory for RL coding environments. It reads what developers complain about on X, keeps a failure mode only when a published paper backs it up, and stacks at least three independent modes into one Harbor task: a ticket, a starting repo and hidden tests.

Every task passes a seven-stage gate before it counts: shape, the reference solution scoring 1 in three runs, the untouched repo scoring 0, every mutation patch caught by a failing test, a red-team shortcut attempt, K cold attempts by a frontier agent, and a fairness check that each failed test maps to a ticket sentence. Calibration then holds the pass rate near 25%. A task everyone solves, or no one solves, teaches nothing; one that is solved some of the time gives a learning signal. Too easy adds a criterion from a fresh failure mode, too hard drops the case family most attempts miss.

The self-improving part: each calibrated task records which modes made solvers slip, and the next design samples modes from that history. It started from the six tasks I built at the Frist RL hackathon, where cold Opus 5.5 solved between 1 of 4 and 3 of 3.

Python, Harbor, Docker, pytest, Claude (author, judge and solver models)

SilverKey 2025–26

The startup I founded and ran for 16 months: a 9-person team shipping web and mobile apps wired into eXp Realty, DocuSign, ATTOM and Plaid, with a ranking model that learns each buyer's taste.

code ↗

read more

SilverKey was my startup. I was Founder and CEO from April 2025 to August 2026 and led a 9-person team. It was an operating system for home transactions, with a React web app, a React Native app, a Flask API and an OpenAPI contract in one monorepo. It integrated eXp Realty, DocuSign, ATTOM and Plaid.

I architected the property ranking. Each home gets two scores for each buyer. One is the cosine similarity between the buyer's preferences and the listing, both embedded with all-MiniLM-L6-v2. The other is an LLM's compatibility judgment. The final score blends the two with weights learned per user: an L2-regularized logistic regression predicts likes from the two scores, and its coefficients, normalized, become that buyer's blend. Personal weights need at least 10 impressions and one like, and retrain after 10 more. Until then, new buyers borrow the weights of a cohort based on budget, age, zip and home type.

I also built an LLM contract-extraction pipeline that feeds a per-state compliance engine, for example for FEMA flood zones.

The demo runs the real web app and API locally on an empty database. Listings come from a paid MLS feed, so search shows no homes.

React, React Native, TypeScript, Flask, PostgreSQL, Redis, Celery, OpenAPI, sentence-transformers, scikit-learn, AWS

Kusama 2026

A painting medium for RL agents where the same program always renders byte-identical pixels, so art rewards can be replayed and checked. Novelty is scored against 20,000 CLIP-embedded museum works.

code ↗

read more

Kusama is a painting medium I built as the ground floor of an RL environment for artistic judgment. An agent never outputs pixels. It writes a JSON program, a tree of typed nodes with no free code, and changes it only through eight kinds of bounded edits. p5 and p5.brush draw the program inside a pinned headless Chromium on software WebGL.

The point is determinism: under one pinned configuration, the same program renders to a byte-identical canonical.png. That makes runs replayable and rewards checkable. Every step goes into a hash-chained log, and a finished run replays byte for byte with the model unplugged, so scores can be rebuilt from the record alone. To get there, the renderer warms up until two frames agree and returns only once two consecutive renders hash the same.

For novelty, I embedded about 20,000 public-domain works from the Cleveland Museum of Art, the Met and the Art Institute of Chicago with CLIP. A painting's novelty is one minus its cosine to the nearest one.

In the demo, a second render in a fresh browser gave the same sha256, and 11 committed goldens check this on every test run.

TypeScript, Node, p5.js, p5.brush, Playwright, headless Chromium, JSON Schema, CLIP (ONNX), Claude Sonnet (agent policy), Claude Opus (judge)

Concept discovery 2024

A 5.6M-parameter AlphaZero-style chess agent and a pre-registered test of feature-diverse search: 41.5% vs 35.0% of 200 held-out mates at 3,072 simulations.

code ↗

read more

At the Georgia Tech Research Institute I asked a narrow question: at a fixed search budget, does exploring candidate moves with different chess features help a small AlphaZero-style agent find correct moves that its own policy ranks low?

I trained a 5.6-million-parameter network in TensorFlow with supervised tactics, Monte Carlo tree search and self-play, then froze it and compared four ways of spending the same search budget: standard PUCT, quality-only, random, and feature-diverse allocation. The benchmark is 200 held-out forced-mate positions from 175 source families, graded by a forced-mate verifier I wrote that checks every legal defence. No chess engine or language model is used.

Feature-diverse search came out ahead at every budget: 32.5% against 29.0% at 1,024 simulations, and 41.5% against 35.0% at 3,072. But the 95% interval at the main budget, -1.5 to +8.8 points, includes zero, so the pre-registered verdict is inconclusive. The one interval that excludes zero is on positions the policy ranks outside its top three: +7.6 points over quality-only.

Python, TensorFlow, MCTS, python-chess, bootstrap statistics

DealRoom 2026

A synthetic deal environment for tool-using agents, graded by a deterministic verifier: Qwen3 8B closed 13 of 32 deals, Llama 3.1 8B 1 of 46. Then SFT vs SFT + RL on Llama.

code ↗

read more

DealRoom is a synthetic deal environment for testing and training tool-using language models. An agent has to close a fictional transaction: gather evidence, get authority, draft the right amendment, collect signatures on that exact revision before the deadline, commit to proceed or cancel, and report what happened. It works through seven typed tools, and a plausible explanation, an informal agreement or an unsigned draft does not count.

A deterministic Python verifier scores the final state: authority, signatures, deadlines, buyer constraints and the structured final claims, with no LLM judge. Inspect AI runs the agent loop, and a local React research console shows model results, trajectories step by step, and grading.

On 48 generated scenarios, Qwen3 8B passed 13 of 32 scored tasks and Llama 3.1 8B passed 1 of 46. Budget limits stay unscored, so the two cover different subsets. I then trained Llama with supervised fine-tuning and with SFT followed by RL; each passed the same 2 of 64 held-out tasks, so RL added no measured gain.

Python, Inspect AI, Ollama, MLX LoRA, React, TypeScript

Kusama studio 2026

A frozen vision-language model directing a frozen image model, every edit saved with its lineage. Its scale edit touched 1.65% of the image and changed none of the 1,031,297 protected pixels.

code ↗

read more

Kusama Studio is the second version of Kusama. Instead of a hand-built medium, a frozen vision-language model directs a frozen image model. Qwen3-VL-8B-Instruct reads a reference packet and the current image, then proposes one concrete change and its expected effect. FLUX.2-klein-base-4B generates or edits the image. Nothing is trained, and both run locally on a 36 GB M4 Max, one after the other to fit in memory.

Every proposal, mask, image, hash and cost is saved with its parent, so each work carries a lineage tree. Model choices and human judgments are stored apart, and only a person advances a work.

The clearest result is a scale experiment. Qwen directed shrinking a hiker to one-third size. FLUX repaired a patch of 1.65% of the image, none of the 1,031,297 protected pixels changed, and the measured height ratio was 0.3365. Asked whether the smaller figure changed the feeling of vastness, the human reviewer said yes. Qwen's first unguided edit was less clear: the reviewer wasn't sure it felt any more vast.

Python, PyTorch (MPS), Diffusers, Transformers, FastAPI, SQLite

Shared whiteboard 2026

A real-time multi-user whiteboard built as a timed take-home: transactional versioning so racing edits never tear a shape. 26 of 26 concurrency checks with 5 users, 3 runs in a row.

read more

I built this real-time collaborative whiteboard as a timed take-home for Mechanize. It is meant for design reviews where 2 to 5 people on a call edit the same canvas, often the same shapes at once. It has accounts, invites, four shape types, live named cursors and per-user undo and redo, and canvases persist.

The hard part is keeping everyone consistent. Every edit is one Postgres transaction. It bumps a per-canvas sequence number under a row lock, so edits are serialized and that number becomes the shape's version. Only after the commit does the server broadcast the new row. Each client keeps the highest version it has seen, so a late or out-of-order frame can never move anything backwards. A shape's position and size are replaced as one unit, so a drag and a resize that race end as one user's shape, never a mix of both. Deletes are tombstones, so a late drag can't bring a shape back. Undo just sends the inverse of my own edit through the same path.

Before submitting, I ran a scripted test with 5 users on one canvas, firing edits at the same time: 26 of 26 checks passed on 3 runs in a row.

React, TypeScript, Vite, FastAPI, WebSockets, PostgreSQL (asyncpg), Docker Compose

Rent roll reader 2024

The core of OM-Analyzer, where I was CTO: an OCR pipeline that turns scanned broker rent rolls into a searchable tenant comps database.

code ↗

read more

As CTO of OM-Analyzer (May–Jul 2024) I built a commercial real estate platform in Python and Flask. Its core turned offering memorandums into a tenant comps database. Brokers' PDFs often hold the rent roll as a scanned image with no text to copy, laid out differently by every broker.

You drag a PDF into the web app. It goes to S3 through a presigned upload, then the server finds the rent-roll page. It renders that page at 300 dpi, sharpens it, boosts the contrast and runs Tesseract. A cleaning pass drops note and boilerplate lines and keeps the lines that carry a dollar amount. It splits those lines at known tenant names, with anchor tenants held to their own rent thresholds. Each row is rebuilt from the OCR fragments: "1" "850" becomes 1,850 square feet, the lease end is matched to a 3, 5 or 10-year term, and rent per square foot is checked against annual rent. Rows land in a per-user master Excel sheet, with the property's address checked against a US ZIP table.

In the demo, a scanned seven-tenant rent roll goes in and seven complete rows come out. The sample is synthetic, and it ran locally against mocked AWS.

Python, Flask, Tesseract OCR, PyMuPDF, openpyxl, pandas, AWS S3 and Cognito, Stripe, Docker

Injectable PrEP model 2026

A week-by-week microsimulation and cost-effectiveness model of injectable HIV PrEP for people experiencing homelessness. Its sharpest finding: outreach without the injection is the most cost-effective arm.

code ↗

read more

This is a transmission microsimulation and cost-effectiveness model of long-acting injectable PrEP (lenacapavir, with cabotegravir as a comparator) delivered to adults experiencing homelessness. It compares five arms: usual care, clinic delivery, two low-barrier outreach arms, and a control arm that gets the same outreach with no injection. The model tracks people week by week: infection through mixing groups, the care cascade, delivery capacity, refusal and missed visits, then costs and QALYs. Paired random streams make two identical arms come out exactly identical.

An important caveat: most inputs are hypothetical placeholders, and 107 of 118 parameter rows have no source. It is a structure for a decision, not an answer to one. Within those assumptions, three findings stand out:

  • Outreach with no injection (arm E) is the most cost-effective arm, at $84,691 per QALY over 5 years.
  • The break-even dose price runs from −$443 to $20,478, depending on what an averted infection is allowed to be worth.
  • Elimination can't be bought. Saturating delivery takes incidence from 1.337 to 0.163 per 100 person-years, and 63% of the infections left come from outside the population.

Python, PyTorch, NumPy, pandas, matplotlib, pytest

reels-edits 2026

A dashboard that cuts images to the beat as a seamless loop. In the demo every cut landed within 16 ms of the beat.

code ↗

read more

Reels Edits is a local dashboard I built for making short, beat-synced image edits with Claude Code. Claude pulls candidate images only from a whitelist of sites, I keep or reject every one in the dashboard, and the order I keep them in becomes the edit order. Claude never finalizes an edit with an image I haven't kept.

The renderer does the timing. It fits the track's tempo and first-beat offset with librosa, sizes the edit to a whole number of bars between 7 and 12 seconds so the music keeps its rhythm when the video loops, and cuts on a repeating pattern of sixteenth notes. Every image gets the same grade, and the last shot is the kept image closest in colour to the first, so the loop seam is hard to see. A checker then measures the finished video against the rules.

In the demo, with 12 public-domain paintings and a generated 124 BPM beat, it found 123.96 BPM and made 12 cuts in 6 bars over 11.63 seconds. The worst cut was 16 ms off the beat, and every check passed.

Python, librosa, NumPy, Pillow, ffmpeg, Claude Code
